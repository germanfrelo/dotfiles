# Standardize Configuration Docblocks and Section Headers

## Context and Problem Statement

Configuration files tracked across this repository (such as Git, chezmoi, Ghostty, ncdu, npm, SSH, Zsh, and EditorConfig) evolved with inconsistent top-of-file documentation blocks and section dividers. Some files used 40-character or 71-character `=` banners, others used bare `# Documentation: <URL>` lines or lacked headers entirely, and templated files included the word `"template"` in `#` comments that rendered into non-template target files on disk. Similarly, section headers varied between 5-hyphen uppercase banners (`# ----- SECTION -----`), 3-hyphen title-case banners (`# --- Section ---`), and plain `# Title` comments that blended into adjacent prose comments.

How should top-of-file docblock banners, section headers, and subsection headers be structured and scoped across `#`-commented configuration files in this repository?

## Decision Drivers

- Must establish a clear visual hierarchy across four comment tiers: file docblock (L1), section (L2), subsection (L3), and explanatory prose (L4).
- Must differentiate sections from subsections using both typographical case and a proportional delimiter length.
- Must ensure comments rendered by chezmoi templates remain accurate in their target destination files on disk.
- Must eliminate redundant filler words (such as `"file"` or `"Documentation:"`) in docblock titles and URLs.
- Must avoid adding custom banners to files that are programmatically rewritten by external CLI tools or auto-generated by wizards.

## Considered Options

- Option 1A: 40-character `=` docblock banner with `<Scope/Tool> configuration` title and bare canonical URL.
- Option 1B: Ad-hoc single-line `# Documentation: <URL>` comments or `<Tool> config file template` titles.
- Option 2A: 2:1 hyphen symmetry—6-hyphen `UPPERCASE` sections (`# ------ SECTION ------`) and 3-hyphen `Title Case` subsections (`# --- Subsection ---`).
- Option 2B: 5-hyphen `UPPERCASE` sections (`# ----- SECTION -----`) with plain `# Title Case` subsections.
- Option 2C: Markdown-style `# ## SECTION` or multi-line ASCII box headers.
- Option 3A: Selective application to human-authored `#`-commented configs, excluding CLI-mutated and wizard-generated files.
- Option 3B: Universal application across all tracked configuration files.

## Decision Outcome

Chosen options:

- Option 1A (40-character `=` docblock banner with `<Scope/Tool> configuration` title and bare canonical URL), because it provides a uniform visual anchor at the top of every configuration file, distinguishes scope where relevant (such as `Global Git configuration` vs. `User npm configuration` vs. `Project npm configuration`), and avoids rendering misleading `"template"` labels into target dotfiles.
- Option 2A (2:1 hyphen symmetry—6-hyphen `UPPERCASE` sections and 3-hyphen `Title Case` subsections), because giving parent sections exactly double the hyphen count of subsections (`6` vs. `3`) alongside distinct casing (`UPPERCASE` vs. `Title Case`) separates L2 sections, L3 subsections, and unframed L4 prose comments on two independent visual dimensions.
- Option 3A (Selective application to human-authored `#`-commented configs), because restricting the standard to hand-maintained `#`-commented files prevents conflicts with tools that parse and rewrite their own configuration files (`gh`) or files generated by external wizards (`p10k configure`, Toptal gitignore generator).

### Consequences

- Good, because scanning any human-authored configuration file immediately reveals its tool scope, canonical documentation URL, major sections, and subsections.
- Good, because rendered target files in `$HOME` (such as `~/.config/git/config` and `~/.config/chezmoi/chezmoi.toml`) no longer claim to be templates.
- Good, because L3 subsections (such as `# --- Editor ---`, `# --- Diff ---`, and `# --- Merge ---`) stand out clearly from `# Ref.` and prose comment lines immediately below them.
- Bad, because existing 5-hyphen and 3-hyphen top-level section headers across multiple configuration files must be updated to maintain repository-wide consistency.

### Confirmation

Compliance is confirmed by inspecting the top-of-file docblocks and section headers across the repository's `#`-commented configuration files and verifying template rendering via `chezmoi diff --use-builtin-diff --verbose`:

1. **L1 File Docblock**:

   ```ini
   # ========================================
   # <Scope/Tool> configuration
   # <Canonical Documentation URL>
   # ========================================
   ```

2. **L2 Section Header**: `# ------ SECTION NAME ------` (6 hyphens per side, `UPPERCASE`).
3. **L3 Subsection Header**: `# --- Subsection Name ---` (3 hyphens per side, `Title Case`).
4. **L4 Explanatory Comment**: `# Sentence-case explanation.` followed by `# Ref. <URL>` when citing documentation.

## Pros and Cons of the Options

### Option 1A: 40-character `=` docblock banner with `<Scope/Tool> configuration` title and bare canonical URL

Wraps the configuration title and primary documentation URL inside `# ========================================` delimiters at the top of the file (immediately after any required interpreter or linter directive such as `# shellcheck shell=zsh`).

- Good, because it removes redundant words like `"file"` and `"Documentation:"` while expanding `"config"` to `"configuration"` for a complete noun phrase.
- Good, because omitting `"template"` ensures the comment remains accurate after chezmoi renders `.tmpl` files into `$HOME`.
- Good, because qualifying multi-tier configs (e.g., `Global Git configuration`, `User npm configuration`, `Project npm configuration`) disambiguates global dotfiles from repository-local counterparts.
- Neutral, because files with mandatory leading directives (`#!/usr/bin/env bash` or `# shellcheck shell=zsh`) place the banner immediately below line 1.

### Option 1B: Ad-hoc single-line `# Documentation: <URL>` comments or `<Tool> config file template` titles

Uses unframed single-line comments at the top of files or includes `.tmpl` implementation details in the title.

- Good, because it requires fewer lines at the top of short files.
- Bad, because `# chezmoi config file template` is factually wrong once rendered into `~/.config/chezmoi/chezmoi.toml`.
- Bad, because unframed `# Documentation: <URL>` lines look identical to ordinary inline setting comments.

### Option 2A: 2:1 hyphen symmetry—6-hyphen `UPPERCASE` sections and 3-hyphen `Title Case` subsections

Uses `# ------ SECTION ------` for L2 sections and `# --- Subsection ---` for L3 subsections.

- Good, because parent sections have exactly twice the hyphen count of child subsections (`6` vs. `3`), creating mathematical and visual proportion.
- Good, because combining dash length (`6` vs. `3` vs. `0`) with casing (`UPPERCASE` vs. `Title Case` vs. `Sentence case`) makes L2, L3, and L4 comments unmistakable at a glance.
- Good, because it preserves single-line headers without introducing multi-line ASCII box clutter.

### Option 2B: 5-hyphen `UPPERCASE` sections with plain `# Title Case` subsections

Uses `# ----- SECTION -----` for L2 sections and unframed `# Subsection` comments for L3 subsections.

- Good, because it matches the initial 5-hyphen style introduced in commit `17353b2`.
- Bad, because an odd number of hyphens (`5`) cannot be cleanly halved for subsections.
- Bad, because plain `# Subsection` headers share the exact `# Word` prefix and casing of normal prose comments (`# Ref. ...`), failing to stand out when followed by explanatory comments.

### Option 2C: Markdown-style `# ## SECTION` or multi-line ASCII box headers

Prefixes section titles with Markdown ATX markers (`# ## SECTION`) or wraps every section in 3-line ASCII banners.

- Good, because 3-line banners are highly visible in long files.
- Bad, because `# ##` mixes Markdown syntax into INI, TOML, and shell configuration files.
- Bad, because 3-line banners triple the vertical line count of section dividers in short configuration files.

### Option 3A: Selective application to human-authored `#`-commented configs

Applies the docblock and section standard to [`/home/private_dot_config/private_git/private_config.tmpl`](/home/private_dot_config/private_git/private_config.tmpl), [`/home/.chezmoi.toml.tmpl`](/home/.chezmoi.toml.tmpl), [`/home/private_dot_config/ghostty/config.ghostty`](/home/private_dot_config/ghostty/config.ghostty), [`/home/private_dot_config/ncdu/config`](/home/private_dot_config/ncdu/config), [`/home/private_dot_npmrc`](/home/private_dot_npmrc), [`/home/private_dot_ssh/private_config`](/home/private_dot_ssh/private_config), [`/home/private_dot_config/zsh/dot_zshrc`](/home/private_dot_config/zsh/dot_zshrc), [`/.editorconfig`](/.editorconfig), [`/.gitattributes`](/.gitattributes), and [`/.npmrc`](/.npmrc).

- Good, because every targeted file is hand-maintained and natively supports `#` comments.
- Good, because it leaves [`/home/private_dot_config/gh/config.yml`](/home/private_dot_config/gh/config.yml) untouched so `gh config` / `gh auth` mutations do not clobber custom headers.
- Good, because it leaves wizard-generated files ([`/home/private_dot_config/zsh/dot_p10k.zsh`](/home/private_dot_config/zsh/dot_p10k.zsh) and [`/home/private_dot_config/private_git/private_ignore`](/home/private_dot_config/private_git/private_ignore)) untouched.

### Option 3B: Universal application across all tracked configuration files

Forces top-of-file banners onto every configuration file in the repository regardless of generator or tool mutation behavior.

- Good, because there are zero exceptions to remember.
- Bad, because CLI tools that serialize their own config state (`gh`) overwrite or misplace custom top banners.
